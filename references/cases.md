# 시험실 에러 케이스 14개

아래는 2026-09-30에 조사한 로컬 `feature/DTH-aisa-integration` 코드와 Figma를 바탕으로 한 후보 절차다. 서버 버전과 현재 요청을 확인한 후 적용한다. 모든 항목이 자동 재현 가능하다는 목록이 아니다. UI 구현 상태로 세팅 가능 여부를 결정하지 않는다.

각 API 케이스는 origin과 HTTP 메서드를 확인한 뒤 `network-error` 규칙을 자동 적용한다. A-3만 `http-401`을 사용한다. URL 차단은 DevTools 설정이 아닌 페이지 함수 가로채기를 뜻한다.

공통 절차와 복구는 [브라우저 조작](browser-operations.md)을 따른다. D-2는 제공된 Figma 목록에 없다. ID를 재번호화하지 않는다.

## A-1 시험 정보를 못 받아 시험실이 열리지 않음

- 조건부: `GET /api/exam/dateInfo`를 자동 가로챌 수 있으나 설치 이후 요청에만 적용된다. 이미 로드된 페이지의 최초 조회에는 소급 적용되지 않는다.
- 대기 화면에서 설치 후 같은 문서 내 SPA 진입으로 최초 조회가 발생하는 흐름이 검증된 경우만 준비한다. 새로고침/전체 페이지 이동은 패치를 지우므로 최초 요청 차단 방법으로 안내하지 않는다.
- 이미 입장한 시험의 폴링 실패는 A-1과 동일하지 않다. 적합한 흐름이 없으면 최초 진입 조건 재현 불가로 보고한다.
- 복구: helper.restore(). 재입장은 담당자가 결정한다.

## A-2 화면 전체 오류

- 한계: API 실패 모의만으로 React 렌더 오류를 보장할 수 없다. 콘솔 throw, 가짜 DOM 화면, React 내부 조작을 사용하지 않는다.
- 확인: 이 방식으로 정확한 재현 불가. JS 청크는 일반 fetch/XHR 패치로 차단되지 않으므로 자동 대안으로 제시하지 않는다.
- 복구: 변경 없음.

## A-3 로그인 세션 만료

- 자연어: “로그인 만료 페이지”, “세션 만료 화면”, “로그인 만료 상태” 요청을 이 케이스로 연결한다. 사용자가 화면 표시를 요청했다면 규칙 설치만으로 화면이 표시됐다고 보고하지 않는다.
- 세팅: 관측한 axios 비변경성 조회 요청의 origin, 경로, 메서드에 `http-401`을 적용한다. XHR status 또는 fetch Response.status를 401로 모의한다.
- 한계: 실제 세션은 유지된다. 앱의 axios 응답 인터셉터가 해당 요청을 처리해야 만료 UI 경로로 들어간다. 실제 쿠키 삭제나 로그아웃은 하지 않는다.
- 확인: 규칙 설치와 실제 axios 요청 hit를 구분한다. 서버가 401을 반환했다고 보고하지 않는다.
- 복구: helper.restore(). 이미 표시된 만료 화면은 남을 수 있고 재진입은 담당자가 결정한다.

표에서 확정한 뒤 다음 순서로 수행한다.

1. 시험실 코드의 `useSessionExpired`는 axios의 성공/실패 응답 양쪽에서 401을 감지한다. 현재 대상에서도 이 동작이 적용되는지 확인하고, 이미 관측한 앱의 조회 요청을 선택한다. 시험실 `GET /api/exam/dateInfo`는 후보이며 현재 탭에서 실제 요청과 폴링이 확인된 경우만 사용한다. 다른 서비스에 이 경로를 임의로 적용하지 않는다.
2. 설치 스크립트를 페이지 도구로 실행하고 확인한 URL과 메서드에 `http-401` 규칙을 적용한다. network-error는 로그인 만료 모의에 사용하지 않는다.
3. 기존 폴링이 있으면 다음 요청을 기다려 hits와 화면을 확인한다. 폴링이 없고 화면 표시까지 요청받았다면 데이터를 변경하지 않는 앱의 조회/새로고침 버튼임을 확인한 경우 한 번만 누를 수 있다. 전체 페이지 새로고침은 패치를 제거하므로 사용하지 않는다. 제출, 자동저장 유발 편집, 시험 재입장으로 대신하지 않는다.
4. 도구에서 직접 `fetch()`나 새 XHR를 호출하는 것만으로 앱의 axios 응답 인터셉터가 실행되지 않는다. 앱 내부 axios나 React 상태를 임의로 찾아 호출하지 않는다. 안전한 앱 조회 경로가 없으면 `401 모의 준비 완료, 앱 조회 대기`로 보고하고 필요한 다음 행동을 설명한다.
5. 관측된 다음 폴링 또는 한 번의 조회 후 확인한다. 시점을 알 수 없으면 무기한 기다리지 않고 `적용 대기`로 보고한다. hits가 증가하고 만료 안내가 화면에 실제로 보이면 `로그인 만료 안내 표시 확인`으로 보고한다. hits만 증가했다면 `401 가로채기 확인, 만료 화면 미확인`으로 구분한다. 화면의 문구나 오버레이/페이지 형태를 추측하지 않는다.
6. QA를 위해 상태를 유지한다. 복구 요청 시 규칙을 해제하고, 앱의 만료 상태가 남았는지도 알린다. 로그인 버튼 클릭이나 시험 재진입은 자동 실행하지 않는다.

## B-1 감독 기기 연결 끊김

- 한계: fetch/XHR 가로채기만으로 웹캠, 화면 공유, 모바일캠의 연결 상태를 각각 모의하는 방법은 확인되지 않았다.
- 대안: 화면 공유 중지 또는 카메라 권한 변경은 실제 기기 조작이므로 모의 방식에 포함하지 않는다. 사용자가 실제 방식도 허용한 경우에만 기기 종류와 기존 상태를 확인해 별도 안내한다. 필수 기기는 퇴장 타이머가 진행될 수 있다.
- 확인: 모의만 요청한 경우 `현재 수단으로 재현 불가`로 보고한다. 인터넷 차단을 기기별 끊김으로 보고하지 않는다.
- 복구: 대안 실행 시 이전 권한 복원과 기기 재연결이 필요하며 자동 복구를 보장하지 않는다.

## B-2 감독 소켓 연결 끊김

- 한계: fetch/XHR 패치는 기존 WebSocket 연결이나 새 WebSocket 생성자를 가로채지 않는다.
- 조건부 대안: 감독 소켓이 XHR polling을 사용한다는 관측 근거가 있으면 그 정확한 경로와 메서드의 실패를 모의할 수 있다. WebSocket으로 전환된 연결은 영향을 받지 않는다. 사용자가 이 대안을 선택한 경우만 적용한다.
- 확인: `polling 요청 실패 모의`로 보고하며 소켓 단절을 단정하지 않는다.
- 복구: helper.restore(). 재연결 여부는 별도 확인한다.

## B-3 인터넷 연결 끊김

- 한계: 이 스크립트는 실제 Offline 설정, navigator.onLine, 소켓/미디어 연결을 바꾸지 않는다.
- 확인: 정확한 인터넷 단절 모의는 지원하지 않는다. 특정 API의 실패를 원하는 경우 그 요청만 대체 케이스로 선택하도록 한다. 전체 요청 무차별 차단이나 가짜 offline 이벤트를 자동 적용하지 않는다.
- 복구: API 대안을 적용했다면 helper.restore().

## B-4 네트워크 불안정, 감독 영상 품질 저하

- 한계: 이 패키지는 요청 지연이나 WebRTC 패킷 손실/영상 품질 저하를 구현하지 않는다.
- 확인: 현재 방식으로 재현 불가. API 오류를 영상 품질 저하라고 보고하지 않는다.
- 복구: 변경 없음.

## C-1 문제 본문 불러오기 실패

- 세팅: 현재 앱에서 문제 데이터 요청을 확인한 뒤 해당 URL을 차단한다. 후보는 문제 이동 시 `GET /api/exam/quiz`다.
- 한계: 초기 데이터/캐시 때문에 요청이 안 나갈 수 있고, 참고자료도 같은 데이터에 들어 있어 C-2에 함께 영향이 갈 수 있다. 본문만 독립 실패시키는 설정이라고 주장하지 않는다.
- 확인: 공동 데이터 요청 실패로 진행할지 사용자에게 설명한다. 독립 실패가 필수라면 현재 방식의 한계로 남긴다.
- 복구: 차단 해제 후 담당자가 문제를 다시 조회한다.

## C-2 참고자료 목록 불러오기 실패

- 세팅: 별도 목록 API가 관측되면 그 요청만 차단한다. 확인한 코드의 목록은 문제 데이터의 `aisaDescriptive.referenceFiles`에 들어 있다.
- 한계: 별도 API가 없으면 C-1과 같은 요청 실패다. 존재하지 않는 자료 목록 API를 만들거나 URL을 추측하지 않는다. 빈 배열로 바꾸는 것은 조회 실패와 다르다.
- 확인: 공동 실패의 영향 범위를 보고하거나, 독립 실패 조건을 제공할 수 없다고 알린다.
- 복구: 이번 요청 차단 규칙 제거.

## C-3 참고자료 파일 열기 실패

- 세팅: 관측한 `GET /api/quiz/referenceFileUrl` 발급 요청을 차단한다. 특정 파일 본문 실패가 목적이면 다운로드가 fetch/XHR인지 확인한 경우만 그 요청을 대상으로 잡는다. img, iframe, 브라우저 내장 PDF 탐색은 이 패치로 막지 못한다.
- 조건: 자료가 포함된 문제가 필요하다. PDF, CSV, Markdown, 이미지에 따라 실제 다운로드 경로를 확인한다. 파일을 이미 불러왔다면 다시 열 때 새 요청이 나는지 확인한다.
- 확인: URL 발급 실패와 파일 다운로드 실패를 구분한다. 서명된 URL 전체를 출력하지 않는다.
- 복구: 규칙 제거 후 자료를 다시 열도록 안내한다.

## C-4 AI 대화 이력 불러오기 실패

- 세팅: 관측된 `GET /api/llm/exams/{examIndex}/quizzes/{quizIndex}/chat/{chatId}/conversations`만 차단한다.
- 조건: AI 사용 가능 시험에서 해당 세션이 존재해야 한다. 메타데이터 조회나 답변 스트림까지 함께 차단하지 않는다.
- 확인: 캐시된 대화 표시와 실제 이력 재조회 실패를 구분한다. 이미 열린 대화의 화면만 보고 적용 여부를 단정하지 않는다.
- 복구: 규칙 제거 후 담당자가 이력 재조회를 수행한다.

## D-1 답안 제출 실패

- 세팅: `/api/quiz/submitAnswer` 요청을 차단한다. 자동저장 API까지 막지 않는다.
- 조건: 제출 가능한 테스트 답안이 필요하다. 요청 확인을 위해 정상 제출을 먼저 실행하지 않는다.
- 확인: 규칙 활성화까지 보고하고 담당자가 제출 버튼을 누르게 한다. 일반 네트워크 실패이며 서버 500/검증 오류와 구분한다.
- 복구: 규칙 제거. 재제출은 자동으로 수행하지 않는다.

## D-3 AI 대화 초기화 실패

- 세팅: 관측된 `/api/llm/exams/{examIndex}/chat/{chatId}/reset` 요청을 차단한다.
- 조건: 초기화가 가능한 대화 세션이 필요하다. 초기화 후 조회만 막으면 서버에서 대화가 이미 초기화됐을 수 있으므로 reset 요청 자체를 대상으로 한다.
- 확인: 초기화 버튼은 담당자가 누르게 한다. UI가 토스트인지 알림인지 판정하지 않는다.
- 복구: 차단 해제. 정상 초기화를 자동 재실행하지 않는다.

## D-4 신분증 제출 실패

- 세팅: `/api/exam/identification/upload` 요청을 차단한다.
- 조건: 신분증 기능이 활성화된 시험에서 테스트용 이미지로 준비한다. 요청을 확인하려고 실제 신분증을 먼저 제출하지 않는다.
- 확인: 업로드 전 차단 규칙을 확인하고 제출은 담당자에게 맡긴다. 이미지 내용을 출력하거나 저장하지 않는다.
- 복구: 규칙 제거. 재업로드는 자동 실행하지 않는다.

모든 API 규칙의 해제는 `window.__examBrowserQA.restore()`를 사용한다. 새로고침하면 패치가 사라지므로 재조회와 전체 페이지 새로고침을 구분한다.
